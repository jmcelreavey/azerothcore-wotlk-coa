# G5b - Runemaster automated audit (145 open "Spell Script / Aura Handler Not Implemented" reports)

Method, modelled on the merged Cultist audit PR #4717 (`c544ef619`): for every report the spell was checked
against, in this order, the effective client data as mirrored by the Ascension DB, the repo's own data
(`modules/mod-spellbook/src/SpellbookTreeSpellData.h` for obtainability, `data/sql/updates/pending_db_world/`
for `spell_proc` / `spell_script_names` / `spell_ranks`) and the core handler that owns the effect type.
These reports are generated by grepping for a spell id and finding zero hits, so most are false positives:
the ability works from the DBC alone.

**Data sources.** Ascension DB spell records (name, tooltip, effect aura types, level, class, tree refs and the
per-field change history) for every id; `apps/coa-dbc` was *not* usable here because this machine has no client
DBCs, so any conclusion that depends on a field the ADB renders as `Unknown` is recorded as needing the client
DBC rather than guessed. There is no build, database or game client on this machine: nothing below was compiled
or run.

## The 29 confirmed gaps, grouped

**A. `SPELL_AURA_PROC_TRIGGER_SPELL` / `SPELL_AURA_PERIODIC_TRIGGER_SPELL` on a passive talent, with no
`spell_proc` row and no script** (18 reports). The DBC gives the passive a proc aura whose TriggerSpell is 0, so
nothing in the core has anything to fire. Each is a small, self-contained clause, but they are 18 separate
mechanics spread over the whole Runemaster tree and they share one fix shape: a
`spell_proc` row or one entry in a class hook keyed on the talent id. Doing them one issue per PR would be 18
PRs; they are listed here as one unit of work.

- #1941, #1948, #1991, #2250, #2727, #2734, #2742, #2745, #2746, #2767, #3100, #3148, #3193, #3194, #3195, #3655, #3670, #3907

**B. `SPELL_AURA_OVERRIDE_CLASS_SCRIPTS` that the core never reads** (2 reports, #3185, #3300).
`AuraEffect::HandleNoImmediateEffect` is bound to aura 112 (`src/server/game/Spells/Auras/SpellAuraEffects.cpp:177`)
and the only MiscValues the core acts on are hardcoded: 7801 at line 559 and 7282 at
`src/server/game/Spells/Auras/SpellAuras.cpp:1489`. Glyphic Destruction 800758 (value 100) and Melting Runes 803013
(value 25) therefore do nothing. The Cultist audit fixed the same shape for Ranger (issue #2495, Serrations), so
there is a precedent for binding an `AuraScript` on the affected damage path.

**C. A named clause that the native effects on the same record do not cover** (1 report, #3149 Frigid Elements:
two `ADD_FLAT_MODIFIER` spell mods work; the `SPELL_AURA_DUMMY` 10 that widens Frigid Fusion never applies).

**D. An effect the Ascension DB cannot name, so the report cannot be classified without the client DBC**
(8 reports: #2732, #3290, #3366, #3652, #3653, #3654, #3679, #3741). Each renders as `Apply Aura: Unknown`,
`Apply Area Aura (Raid): Unknown` or a bare `Unknown` effect. The named clauses on the same records are native
and do work. #3741 Leyline Disturbance 560540 is in this bucket rather than "already worked" because the raid
haste aura is the unnamed one; only its `SPELL_AURA_MECHANIC_DURATION_MOD` half is native.

**E. Tooltip and DBC disagree** (1 report, #2737 Shroudwalker 705563: the tooltip says Warpdagger incurs no
cooldown while Runeshroud is active, the DBC carries an `ADD_FLAT_MODIFIER -25000` instead). Which of the two is
right is a maintainer decision, not a code fix.

## Why no `fix/runemaster-audit` branch

The only real bug the sweep found is #3651 Eternal Magic, and it is fixed on `fix/runemaster-player-reports`
(the report names the same spell as the player report #5254, so it belongs with it). The 29 gaps plus the one
tooltip mismatch are real, but none is both small and safe to land blind: each needs either a `spell_proc` row
whose ProcFlags, SchoolMask and SpellFamilyMask I cannot verify without the client DBC, or a new damage-path
hook. Landing 30 unverified mechanics in one PR would be exactly the half-done change the brief rules out, so
the branch is not created and the gap list above is the deliverable. **The recommended next unit of work is the
18 group-A reports**: they share one mechanism, and one `spell_proc` seed file plus a gameplay scenario per
clause would close them together.

## Caveats the reviewer should know

- **Rank siblings.** 13 reports name a higher rank ("2 ranks: 705556, 705557"). The Ascension DB annotates a real
  talent node with `Class: Runemaster - Runemaster - Tree (row, col)` plus a `tree:` reference; a higher rank
  carries neither, so it is classified by its own record. Talent rank chains live in the client's
  `CharacterAdvancement.dbc` (read at runtime by `src/server/coa/AscensionCoATalentData.cpp`), which this
  machine cannot read, so a higher rank whose rank-1 sibling is a tree node would be missed. All 13 were checked
  against `SpellbookTreeSpellData.h` for their own id first.
- **`AscensionStockCoefficientData.h` hits are not evidence.** That header lists ~2700 Runemaster spells for a
  coefficient sweep, so it appears in nearly every grep and says nothing about whether a mechanic works.
- **The ADB `history` field** is the only record of client-side changes. It is why #3651 could be classified at
  all, and it shows the Palm Sigils were changed twice on 2026-08-01/13 (a stance-mask flip and the removal of
  `SPELL_ATTR0_NOT_SHAPESHIFTED`), i.e. that data was still moving when the reports were filed.
